# 工作流：蓝图生成（blueprint）

> **本步是一切工程文件的起点**：先生成蓝图，再生成工程。
> 蓝图 = 工程的**唯一事实源**（single source of truth）—— 后续一切创建与修改，**结构 / 兵力 / 任务类先改蓝图再改工程**；脚本内容在 §4 裁剪后以工程文件为准（见 `3_generate.md` Step 6）。
>
> **为什么必须有蓝图**：实测中所有运行发散，都源于智能体在上下文清理 / 压缩后遗忘了「要求」与「工程结构」。
> 蓝图把**用户输入 + skill 规则 + 目标工程结构**固化为一个文件；即使上下文大量丢失，按蓝图执行即可恢复现场、收敛结果。
>
> **产出物**：`<想定名>.md`（工程文件夹根目录）。

---

## 0. 前置：输入已解析

本步之前必须已完成 `workflows/1_intake.md` 的 **6 项结论**（想定名 / 阵营与兵力 / 任务与过程 / 体系关系 / 配置及来源 / 待确认清单）。
未解析 → 先走 `1_intake.md`，**不要跳过**。

## 1. 命名与位置（铁律）

| 项 | 规则 |
| :-- | :-- |
| 蓝图文件名 | `<想定名>.md` |
| 工程文件夹名 | `<想定名>/` |
| 入口文件名 | `<想定名>.txt` |
| 校验 ZIP 名 | `<想定名>.zip` |

**四者严格同名**（大小写不敏感亦不得重复）——这是校验接口「启动文件唯一」判定的前提。蓝图位于工程根目录，与 `<想定名>.txt` 同级。

## 2. 生成蓝图

**模板**：`blueprints/skeleton/blueprint.md.tpl`（8 节结构，占位符 `{{...}}`）。

**填充依据**（按优先级）：

| 蓝图节 | 内容来源 |
| :-- | :-- |
| §0 元信息 | 想定名（结论 1）、输入来源、仿真起止（结论 3） |
| §1 简介与任务想定 | 实验筹划原文摘录 + 6 项结论表 |
| §2 文件结构 | `blueprints/layout/layout.md`（必建 4 根文件 + 目录按需 + `output/blank_empty.txt`） |
| §3 工程详细说明 | 结论 2 / 4 + `blueprints/layout/assembly.md`（装配链）+ `blueprints/fragments/`（组件职责）+ `blueprints/cases/`（同类案例） |
| §4 完整脚本全文 | `blueprints/skeleton/` 模板 + `fragments/` 片段 + `cases/` 案例全文；**细化到每个文件的相对路径与全文** |
| §5 AI 自检结论 | 见本文 §3 |
| §6 变更记录 | 初版 v1 |

**规则**：

1. §4 的每个文件块即后续工程文件的**唯一生成依据**——蓝图写完，工程文件的全部内容就确定了。**§4 只在生成期有效**：`3_generate` 一致性自检通过后立即裁剪为指针（见 `3_generate.md` Step 6）。
2. 语法规则只认 `blueprints/`（skeleton / fragments / cases）与 `knowledge/`，**不得凭空自造 AFSIM 语法**。
3. 缺省值按 `SKILL.md`「缺省值」与 `blueprints/layout/defaults.md` 补全，并在 §1 结论 5 标注来源。

---

## 3. AI 自检（蓝图生成后、工程生成前）

### 3.1 需求与结构一致性（必做）

逐项核对并在蓝图 §5.1 记录结论：

- 蓝图覆盖 intake 6 项结论，无缺项；
- 蓝图与用户输入一致（兵力 / 阵营 / 任务无编造、无擅改）；
- 布局符合 `layout.md`（必建 4 根文件、目录按需、`output/blank_empty.txt` 存在）；
- 命名四者同名；
- §4 全文与 §2 文件结构一一对应（无多余、无遗漏）；
- `SKILL.md` 16 条硬约束逐条对照。

### 3.2 语法预检（必做）

逐文件过一遍可预判项（**不替代**第 4 步语法校验）：块闭合、数值带单位、坐标 `d:m:s`、`platform_type` 带 `WSF_PLATFORM`、`include` 目标存在、`file_path .` 在第一个 `include_once` 之前、顶层装配用 `include_once` / 块体内联裸片段用 `include`。

**拿不准就查摘抄库**（`knowledge/corpus/00-index.md` §六）：凡是「这个命令 / 参数该怎么写」没把握的块，先按 §六 检索官方 demo 原文，照其结构写；**查不到再按手册推演**，且推演项必须在下游语法校验中重点验证。摘抄库只学结构，**禁止照抄其中数值**。

### 3.3 仿真时长校核 ★（最重要，不通过不得进入工程生成）

> **历史实测最高发问题：仿真时长小于任务实际所需时长**——人类播放罗盘文件时想定的任务还没结束，仿真就先到了 `end_time`。

步骤：

1. 从蓝图 §3.4「运行时序与数据流」提取**任务时间线**，计算任务结束时间 `T_task`（分钟）。
2. 缓冲 = max(T_task × 0.2, 2 m)。
3. `end_time` 必须 ≥ T_task + 缓冲；不足则**修正蓝图 §4 的 `end_time` 与 `run.json` 的 `continueTime`**（分钟，与 end_time 一致）。
4. 入口文件 `start_date` / `start_time` 与 `run.json` 的 `scenariosTime` 必须一致。
5. 结论写入蓝图 §5.3。

> 若实验筹划未给出明确任务时间线 → 按缺省 `10 m`，并在 §5.3 与交付说明中标注「任务时长未明确，采用缺省值，请用户确认」。

## 5. 铁律（全程有效，跨上下文压缩依然适用）

1. **蓝图分层维护**：结构 / 兵力 / 任务 / 配置语义类变更，第一步永远是改 `<想定名>.md`（§6 记一条），再据蓝图改工程；脚本内容在 §4 裁剪后**直接改工程**，变更记入 §6。
2. **蓝图即事实源**：生成期工程文件必须与蓝图 §4「逐字符一致」，不一致时以蓝图为准修正工程（除非用户要求改设计——那仍然是先改蓝图）；**裁剪后脚本以工程为准，§6 是唯一差异记录**。
3. **上下文恢复**：智能体若感觉「忘了要求 / 忘了结构」（尤其上下文被清理或压缩后），立即重读 `SKILL.md`（按需回顾）与本蓝图，再继续操作。
