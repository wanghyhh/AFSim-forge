# afsim-forge-skill

> **让模型从自然语言直接生成 AFSIM 脚本文件的skill** —— 产出的不是零散片段，而是**一整套完整的、可直接运行的多文件 AFSIM 工程**。

## 这是什么

**一个让大模型从自然语言直接写出 AFSIM 脚本文件的技能。**

你描述任务、仿真目的、过程、包含兵力，模型直接产出 AFSIM 的 `.txt` 脚本文件——不用你手写、不用你拆结构、不用你事后补漏。

它的亮点不在于"能写脚本"，而在于**写出的是一整套完整的、可直接运行的多文件工程**：

> AFSIM 的想定**不是"一个 `.txt` 写完就行"**。标准做法是**多文件工程**——9 个根文件 + 14 个目录，用 `include_once` 自上而下装配，`file_path .` 锚定路径基准，平台类型 / 组件 / 实例各落在不同目录里。
> 单文件脚本在 AFSIM 里往往**跑不起来**：缺 `output/` 目录、漏登记 `setup.txt`、`include` 路径相对谁搞不清、块放错文件——任何一处都直接报错。

`afsim-forge` 把"从自然语言到可运行多文件工程"这条路打通：

```
实验筹划（自然语言）  ┐
                      ├─→ 输入解析 → 建骨架 → 分模块生成 → 语法校验 → 交付
想定编辑（JSON，可选）┘                                    ↑___________|  闭环纠错
```

### 为什么强调「多文件」

| | 直接让模型写 AFSIM | **afsim-forge** |
| :-- | :-- | :-- |
| **产出形态** | 通常是一段**单文件脚本** | **完整多文件工程**：9 根文件 + 按需目录 + 装配链 |
| **结构归属** | 靠模型印象，块该放哪个文件不确定 | 结构权威固化，**块 → 目录有明确映射表** |
| **路径与装配** | `include_once` 常写错（相对谁？） | `file_path .` + **相对工程根**，规则写死 |
| **完整性** | 容易缺 `output/`、忘登记 `setup.txt` | 自检清单逐条过，缺项必暴露 |
| **正确性** | 无从验证，只能拿去试 | **必须过语法校验**，`valid=true` 才允许交付 |

### 「可直接运行」的含义

工程**结构完整 + 装配链闭合 + 语法校验通过**——拿到 AFSIM 里就能跑。

本 skill 本身**不代跑仿真**（不跑、不回放、不取结果），这是有意划的边界：它只保证"交给你的是一个能跑的工程"，跑与不跑、怎么跑，由你和 AFSIM 决定。

## 核心特性

| 特性 | 说明 |
| :-- | :-- |
| **★ 完整多文件工程** | 产出的是 **9 个根文件 + 按需目录**的整套工程，不是单文件片段；`include_once` 装配链、`file_path .` 路径基准、`output/` 占位**一次到位** |
| **★ 可直接运行** | 结构完整 + 装配闭合 + 语法校验通过；**少一个文件、错一行 include 都过不了闸门** |
| **★ 自然语言直达** | 一句"某区域防空拦截想定，红方 1 部预警雷达…"就能开工，不需要你懂目录结构与装配顺序 |
| **两类输入契约** | 自然语言的**实验筹划**（必需）+ 格式不定的**想定编辑 JSON**（可选）。JSON 有就读、没有就生成 |
| **结构权威唯一** | 目录树、根文件职责、块→目录映射、装配顺序全部固化，不靠模型"凭印象" |
| **可复制骨架** | 9 个根文件 + `run.json` 的 `.tpl` 模板，另附一个**可一次过校验**的最小工程 |
| **11 类组件片段** | platform / sensor / weapon / mover / comm / processor / network / medium / side / signatures / weapon_effects |
| **5 个完整案例** | 每个案例一份文档：详细说明 + 逐文件全文，全部实测通过语法校验 |
| **校验即闸门** | 生成后**必须**调用校验工具，`valid=true` 才允许交付与归档 |
| **三层教训库** | 报错现象（E）→ 归类（L）→ 根因与修法，越用越准 |
| **渐进披露** | 入口文件只放规则与索引（约 210 行），知识按需加载，不一次性塞满上下文 |

## 输入契约

### 两类输入

| 输入 | 形式 | 必需 | 作用 |
| :-- | :-- | :-: | :-- |
| **实验筹划** | 自然语言文本 | ✔ | 整个想定的详细内容：**任务、仿真目的、过程、包含兵力**等 |
| **想定编辑** | JSON 文本（`scenarioJsonData`） | ○ | 一些**必要的配置**；**格式不定** |

### 三条核心规则

1. **JSON 有就读、没有就生成** —— 提供了必须按语义落地（不忽略、不取一半、不丢字段）；没提供就按实验筹划 + 缺省值生成，**不得因此停下追问**。
2. **优先级**：`JSON 显式给出 > 实验筹划明确描述 > 缺省值`。配置项冲突以 JSON 为准并标注被覆盖值；**想定内容（兵力 / 阵营 / 任务）冲突必须问用户**。
3. **实验筹划必须拆成工程要素**（想定名 / 阵营与兵力 / 任务与过程 / 指挥与通信 / 传感器与武器 / 指标口径），拆不出就按缺省补，**不编造兵力与性能参数**。

### JSON 格式不定怎么办

按**语义识别**，不按固定 schema 解析：

| JSON 里出现什么 | 落到哪 |
| :-- | :-- |
| 工程 / 想定 ID（如 `scenariosId`） | `config/run.json` 的 `scenariosId`（**原值照抄**，此时不置 0） |
| 时间 / 时长 | `config/run.json` 的 `scenariosTime` **＋** 入口 `start_date` / `start_time` / `end_time`（两处必须一致） |
| 记录开关 / 步长 / 倍率 / 线程 / 启动模式 | `config/run.json` 对应字段 |
| 阵营 / 兵力 / 数量 | 与实验筹划**交叉校验**；一致落 `side/*.txt`，不一致问用户 |
| **认不出的字段** | **原样并入** `config/run.json`（不改名 / 不删 / 不合并嵌套），交付时列「未识别字段清单」 |

**三条铁律**：① 不丢字段；② 不改语义（字段名 / 嵌套 / 数组顺序保持原样）；③ 不猜单位。

## 输出：一整套多文件工程

产出的**不是一个脚本文件，而是一个工程目录**——符合标准 AFSIM 多目录结构，`include_once` 装配链完整闭合：

```
<想定名>/
├── <想定名>.md          ★ 蓝图（唯一事实源，与工程同名；先改蓝图再改工程）
├── <想定名>.txt          ★ 入口（严格同名，与 ZIP 同名；含 file_path . 与装配链）
├── setup.txt                 平台装配清单
├── event_pipe.txt            事件管道
├── global_env.txt            全局环境
├── global_script.txt         公共脚本层（按需）
├── global_struct.txt         自定义数据结构（按需）
├── global_route.txt          全局航路（按需）
├── group.txt                 编组（按需）
├── zone.txt                  顶层区域（按需）
│
├── config/run.json           业务侧运行控制
├── common/                   通用数据表（人类提供）
├── output/blank_empty.txt    输出落点占位（缺了会报错，ZIP 不保留空目录）
├── platform/  sensor/  weapon/  mover/  comm/
├── processor/  network/  medium/  side/  signatures/  weapon_effects/
```

**每个目录放什么、每个根文件管什么、谁 include 谁**，都由结构规则固定下来，不靠临场发挥。

**交付说明**会同时给出：工程目录树、组件清单、**参数来源表**（每个参数标明是 JSON / 实验筹划 / 缺省给的）、未识别字段清单、待人类补齐清单、**脚本行数统计**（除蓝图外所有模型生成的文本文件）、校验结论。

## 快速开始

### 1. 前置条件

- 一个提供 `validate_scenario` 能力的 **MCP 校验服务**（默认方式；无服务时可切换为本地 `mission.exe` 直接调用）
- 支持 skill 的宿主环境

### 2. 安装

把整个目录放到宿主的 skill 发现路径下：

```bash
<SKILLS_HOME>/skills/afsim-forge/
```

目录形态必须是 `<name>/SKILL.md`（**不支持**嵌套 `**/SKILL.md`）。

### 3. 调用

```
/afsim-forge
```

单入口 + 意图路由。进入后按你的话自动分派：

| 你说 | 走哪 |
| :-- | :-- |
| 给出实验筹划 / 想定编辑 | `workflows/1_intake.md` |
| "生成 / 新建 / 做一个 … 工程" | `1_intake` → `2_blueprint` → `3_generate` |
| "先出蓝图 / 先看设计" | `workflows/2_blueprint.md` |
| "校验 / 语法对不对" | `workflows/4_validate.md` |
| "报错了 / 帮我修一下" | `workflows/debug.md` |
| "归档 / 可以了 / 交付" | `workflows/5_deliver.md` |

### 4. 最省事的用法

直接把**实验筹划**贴进来，一句话说清任务、目的、过程、兵力，剩下交给它：

```
实验筹划：某区域防空拦截想定。红方 1 部预警雷达、2 个发射车、4 枚拦截弹，
蓝方 2 架轰炸机从东侧进入。目的是验证从预警到拦截的杀伤链能否在 8 分钟内闭合。
关注探测距离、拦截成功率、反应时间。
```

想定编辑 JSON 有就给，没有它也会按上面的内容生成。

出来的**不是一段脚本，而是一个工程目录**：9 个根文件 + `platform/`、`side/`、`sensor/`、`weapon/`… 各就各位，`setup.txt` 已登记、`output/` 已占位，打包即可过校验。

## 工作流（5 步 + 2 条旁路）

```
1_intake（意图识别）
   ↓ 6 项结论
2_blueprint（蓝图生成）★ 防发散核心
   ├─ 生成 <想定名>.md（唯一事实源，与工程同名，放工程根目录）
   ├─ AI 自检：需求一致性 + 语法预检
   └─ 仿真时长校核：end_time ≥ 任务时间 + 缓冲（实测最高发问题）
   ↓
3_generate（据蓝图生成）
   ├─ Step 1 建目录与骨架
   ├─ T1 ── 骨架校验 ─────────┐
   ├─ Step 3 按蓝图 §4 落盘 ──┤ 未通过 → debug → 再校验（上限 3 轮；
   ├─ T2 ── 每类组件校验 ─────┤        修复先改蓝图，再改工程）
   ├─ AI 自检：工程 vs 蓝图逐字符一致
   └─ T3 ── 终校验 ───────────┘
   ↓ valid=true
5_deliver（交付）
   ├─ 结束判定：valid=true + 用户认可
   ├─ 内容整理：清过程文件，仅留工程（含蓝图）
   ├─ 行数统计：除蓝图外所有模型生成文本文件
   ├─ 后续询问：是否完整跑一次仿真（MCP 全工具 / 本地 mission.exe 备用）
   └─ 归档：staging → verified（只进不出）
```

**两个关键设计**：

1. **蓝图即事实源**：实测中所有运行发散都源于上下文清理后遗忘「要求与工程结构」。蓝图把二者固化为一个文件——**一切创建、修改、修复先改蓝图、再改工程**，即使上下文大量丢失，按蓝图执行即可恢复现场。
2. **增量校验点**：骨架先过一遍、每类组件再过一遍，把错误限制在刚生成的范围里，而不是等几十个文件写完再一起爆。

## 设计原则

| 原则 | 做法 |
| :-- | :-- |
| **不凭空造语法** | 骨架、片段、完整案例都取自实测通过的工程；语法细节查知识库 |
| **结构权威唯一** | 冲突时一律以 `blueprints/layout/layout.md` 为准 |
| **蓝图即事实源** | 先出蓝图再生成工程；一切创建 / 修改 / 修复**先改蓝图、再改工程**；上下文压缩后按蓝图恢复现场，防发散 |
| **skill 目录只读** | 运行期绝不写 skill 目录；产出与教训写工作空间的 `.afsim-forge/` |
| **校验是闸门** | 判据**只看** `data.valid`；语法对错都返回 HTTP 200，禁止用状态码判断 |
| **渐进披露** | L0 入口（规则）→ L1 起步（蓝图/结构/骨架）→ L2 命中（片段/案例/语法）→ L3 报错（教训） |
| **可追溯** | 交付说明逐项标注参数来源，用户能复核每个值从哪来 |

## 硬约束速览

生成时必须逐条自检（完整清单见 `blueprints/layout/layout.md`）：

1. 扩展名一律 `.txt`（不是 `.wsf`）
2. 所有数值必须带单位（`500 m/sec`、`10000 m`、`2 s`、`9500 mhz`）
3. 每个块必须有 `end_*`；`platform_type` 必须写基类型 `WSF_PLATFORM`
4. 坐标用冒号 `d:m:s`（`38:44:52.3n`），不是点号
5. 入口文件**严格同名** `<想定名>.txt`，且与 ZIP 同名
6. 入口文件必须写 **`file_path .`**，且在**第一个 `include_once` 之前**
7. `include_once` 路径一律**相对工程根**（不是相对当前文件）
8. `output/` 必须存在（`blank_empty.txt` 占位，ZIP 不保留空目录）
9. 组件文件头部先 `include_once` 自己的依赖
10. **顶层装配用 `include_once`；块体内联裸片段用 `include`**（用错会让第二处**静默跳过**）
11. 新增平台必须登记进 `setup.txt`
12. 禁止中文路径（AFSIM 对中文路径有缺陷）
13. 禁止编造 `common/` 数据表内容与 `scenariosId`
14. **先改蓝图，再改工程**：工程的一切修改先落 `<想定名>.md`，再据蓝图改脚本
15. **按需回顾**：上下文被清理 / 压缩后，先重读 `SKILL.md` 与工程蓝图，再继续操作

## 验证情况

| 项 | 结果 |
| :-- | :-- |
| 端到端实测（正例 1 + 负例 3 + 修复复校 2） | 全部符合预期 |
| 5 个完整案例（改造前基线 / 改造后工程） | 全部通过语法校验 |
| 最小骨架（替换占位符后直接打包） | `valid=true`，`errors=[]` |
| 项目内路径引用悬空扫描 | 0 条 |

**最有价值的发现**：块未闭合（缺 `end_*`）会报 `Unexpected End Of Data`，且**报错文件/行 ≠ 出错文件/行**（常指向入口文件末行）。修复时须从文件头逐块核对闭合，**不能按 `line` 机械改**。

**未验证项**：输入解析规则尚未用一对真实的「实验筹划 + `scenarioJsonData`」跑通全流程；MCP 工具级冒烟待补做；**蓝图驱动流程（2_blueprint → 3_generate → 5_deliver）尚未端到端实测**，首次使用建议以简单想定验证。
