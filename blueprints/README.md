# blueprints — 工程骨架与案例

> **本目录回答"该长什么样"**：结构放哪、骨架怎么填、片段怎么取、完整工程长什么样。
> 这里全是**可复制/可填空的实物**（`.tpl` 模板、`.md` 案例），**不是**方法论；方法论在 `knowledge/`。

---

## 1. 四个子目录，各管一件事

| 子目录 | 是什么 | 什么时候读 | 权威性 |
| :-- | :-- | :-- | :-- |
| `layout/` | **结构规则**：目录树、根文件职责、块→目录映射、装配顺序、缺省值、`run.json` 字段 | 动手建工程前**必读** | ★★★ **结构唯一权威** |
| `skeleton/` | **可填骨架**：9 个根文件 + `config/run.json` 的 `.tpl`；`minimal/` 是可一次过校验的最小工程 | 从零生成时直接复制 | ★★☆ 与 `layout/` 逐项对齐 |
| `fragments/` | **组件片段**：11 类（platform / sensor / weapon / mover / comm / processor / network / medium / side / signatures / weapon_effects），每个自带依赖 include 头 | 需要某个组件的写法时 | ★★☆ 片段级正例 |
| `cases/` | **5 个完整工程案例**：一案例一文档，含详细说明 + 逐文件全文，全部实测 `valid=true` | 想找"同类工程怎么组织"时 | ★★★ **最可靠的正例** |

### `layout/` 里有什么

| 文件 | 内容 |
| :-- | :-- |
| `layout.md` | ★ 目录树 + 9 根文件职责 + 目录→块类型映射 + 生成自检清单 |
| `assembly.md` | 装配链、入口三要素、`include` vs `include_once`、命名与写法约定、常见装配错误 |
| `defaults.md` | 缺省值（工程级 / 组件级 / 须人类提供的） |
| `run-json.md` | `config/run.json` 字段说明 |

### `cases/` 里有什么

`ad_hoc` · `launcher` · `outer_air_battle` · `ship_ad` · `space_operations` —— 每个案例一份 `.md`，
五段式：元信息 / 文件结构 / 案例详细说明 / 完整脚本全文 / 使用指引。索引见 `cases/README.md`。

## 2. 怎么选：三条路径

| 场景 | 路径 |
| :-- | :-- |
| **从零搭最小可跑工程** | `skeleton/minimal/` 复制 → 替换占位符 → 校验 → 逐步扩展 |
| **要建完整结构** | 先读 `layout/layout.md`（决定文件放哪）→ 用 `skeleton/*.tpl` 填根文件 → 用 `fragments/` 填组件 |
| **找同类工程照抄结构** | `cases/README.md` 挑案例 → 读该案例的 §1 文件结构 + §2 说明 → 按需取 §3 全文 |

## 3. 骨架 vs 实例：为什么模板和案例不一样

`cases/` 与 `skeleton/` **结构逐项对齐**（根文件数量、目录、入口装配链、组件块形态、`output/` 占位方式全一致），但**内容有意不同**：

| 维度 | 案例（实例） | skeleton（骨架） | 原因 |
| :-- | :-- | :-- | :-- |
| 命名 | 具体业务名 `GBI_LAUNCHER`、`TTR_RADAR` | 占位符 `{{PLATFORM_TYPE}}` | 模板要能生成**任意**想定 |
| 数值 | 具体值 `9500 mhz`、`power 1000 kw` | 占位符 `{{FREQUENCY}}` | 无依据时**不编造**，标"待确认" |
| 自动 ID | 工具生成的雪花 ID | 语义化 `{{SENSOR_NAME}}_ANTENNA_SEARCH` | 雪花 ID 无复用价值 |
| 业务脚本 | 含任务管理逻辑（`Map<int,SimTask>…`） | **不含** | 属用户内部业务，不该硬编码 |
| `common/` 数据表 | 含弹道表等大数据 | **只建目录** | 业务数据由人类提供 |
| 缩进 | 部分文件不统一 | 统一缩进 | 模板求可读 |

> **一句话**：案例回答"**这个想定长什么样**"；骨架回答"**这类文件该放什么块**"。
> 骨架是"抽象"，案例是"实例"——**抽象可能有遗漏，实例一定跑得通**；两者冲突时，**以能过校验的案例为准**。

## 4. 使用顺序（推荐）

0. **先解析输入** —— `workflows/intake.md`：把**实验筹划**（自然语言）与**想定编辑**（`scenarioJsonData` JSON，可选）拆成想定名 / 阵营与兵力 / 任务与过程 / 体系关系 / 配置及来源。**没有这一步，后面的目录和文件都无从谈起。**
1. **`skeleton/minimal/`** —— 先跑通"结构 + 校验链路"，别一上来就写几十个文件。
2. **`layout/layout.md`** —— 明确新文件该落到哪个目录。
3. **`fragments/`** —— 按组件类型取片段，填参数。
4. **`cases/`** —— 卡住时找同类案例对照（尤其是 `include` 顺序、`side/` 实例写法、`network` 的 `member`）。
5. **校验** —— 走 `workflows/validate.md`；报错查 `knowledge/lessons/errors.md`。

> ⚠️ 无论走哪条路径：**入口文件里不得 `include_once` 不存在的文件**；**新增平台必须登记进 `setup.txt`**。
